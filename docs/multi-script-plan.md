# Multiple scripts and dashboard control: implementation plan

Status: in progress. This document defines the approved behavior; the
[implementation guide](multi-script-implementation.md) records what has shipped
and what remains.

Follow the [step-by-step implementation guide](multi-script-implementation.md)
for code areas, test gates, and a completion record. This plan remains the
behavior contract.

## Goal

Run several independent Pocketspace scripts in one engine process, while keeping a SteamVR dashboard control available to launch, inspect, reload, and stop each script. Scripts communicate through a bounded publish/subscribe event bus with catch-all subscriptions. A script failure must not discard another script's scene. The dashboard must show useful per-script resource data and distinguish estimates from measured process totals.

## Baseline at the initial design audit

- At the initial audit, `src/main.cpp` accepted one positional script path and drove one active `Scene`. Step 2 replaced that path with catalog launches and instance-scoped rendering and cleanup.
- At the initial audit, candidate reload used a separate QuickJS runtime/context and scene, with a 128 MiB QuickJS memory limit. Scene containers isolated resources *within* a scene. Step 1 added independent live script contexts.
- At the initial audit, renderer and input routing, physics dispatch, callback storage, overlay naming, and statistics included process-global state and scene-local numeric IDs. Steps 0–3 mapped ownership and qualified live interaction and native resources by instance. Per-script telemetry remains planned for Step 9.
- `getEngineStats()` reports process CPU/RAM/GPU measurements and engine allocation estimates. Process measurements cannot honestly be assigned to individual scripts without new instrumentation.
- Named scene saves currently share one directory. Multi-script storage must prevent same-name collisions between scripts; existing development/test saves may be deleted or recreated.
- Keep a single OpenVR connection, input poller, compositor submission loop, EGL context, and engine process. Run QuickJS callbacks on the host thread initially. Multiple OS processes would duplicate host resources and leave cross-script interaction unresolved.

## Approved runtime model

The engine owns a registry of `ScriptInstance` records, each with a stable instance ID, canonical script path, display name, lifecycle state, last error, start/reload timestamps, QuickJS runtime/context, and scene. Reserve instance ID `0` for the engine-owned scratch REPL scene; ordinary scripts receive positive IDs. Allow one live instance per canonical script file; reject duplicate launches clearly. Do not silently turn a second launch into reload. Start with no **user scripts** by default in managed mode, while the scratch scene remains available. Provide an explicit autostart list in one editable configuration file. The dashboard and CLI edit that same file through the engine, using validated atomic writes; external file edits are reloaded with validation and errors are shown without discarding the last valid settings. Validate each entry against the configured script catalog, launch independently, and show individual startup failures without preventing the host or other autostarts from running. A manual stop overrides autostart and automatic error recovery for the rest of that engine session; it does not remove the autostart entry, so the script may launch on the next engine start. The default catalog is a separate user scripts directory, not the repository's examples directory; make its path configurable and discover `.js` files in its subdirectories. Launch scripts only through catalog names; starting the engine with no launch entries leaves the user-script list empty.

Each instance has its own object, panel, light, asset, physics, callback, persistence scope, and cleanup state. Shared input and tracking snapshots are read once per frame, then routed to instances. Rendering collects surfaces from all live scenes in deterministic instance order, retaining each scene's depth, transparency, stereo, and compositor contracts. For model-ray interaction, global selection picks the closest eligible target across scripts for each hand, then uses stable instance ID to break equal-distance ties. Native panel pointer events belong to the overlay SteamVR targets. Input callbacks and events go only to their owner. A held object remains owned by that script until release or its stop/reload.

Lifecycle commands are queued and applied at a safe host-loop boundary: launch, reload, graceful stop, and forced stop only as a last resort for a stalled process (a stalled callback cannot be preempted safely within one process). Running script files retain automatic modification-time reload. Validate and stage a candidate scene before publishing it. A failed launch leaves the instance in an error state; a failed reload keeps the prior scene and records the error. An uncaught `update()` or event-callback exception stops only that script, records the exception and source, and leaves other scripts running. Show a SteamVR notification and a dashboard alert. One global automatic-restart setting controls whether scripts stopped by callback errors are restarted; it is off by default, so a stopped script stays stopped until explicitly started. If enabled, retries must be paced and bounded so a failing script cannot spin in a restart loop. An uncaught scratch callback exception resets only scratch instance `0`, leaving user scripts running. Stopping one instance detaches and releases only its resources. Engine shutdown stops all instances before OpenVR/EGL teardown.

Maintain a healthy host and scratch scene when no user scripts are running. Use catalog launches for startup scripts and later dashboard/CLI commands. Keep current in-scene API IDs unchanged and qualify native keys with instance ID. Add only the event-bus JavaScript API needed for inter-script communication in the first release.

## Inter-script event bus

Expose `publish(topic, payload)`, `subscribe(topic, callback)`, and `unsubscribe(subscriptionId)` to each script, including scratch. Use `space.*` for script-published topics (for example, `space.scoreChanged`); validate this prefix and a bounded UTF-8 topic length. `subscribe("*", callback)` is the catch-all subscription: it receives every published topic from **other** instances, including topics without a specific subscriber; it does not receive the subscribing instance's own publications. An exact-topic subscription does receive its own publication when the topic matches. Exact-topic subscribers and catch-all subscribers both receive an event when they match; an instance can have more than one subscription. Reserve `*` as a subscription selector, not a publishable topic. Reserve `engine.*` for engine-originated lifecycle and diagnostic events: scripts and scratch can subscribe to exact `engine.*` topics or receive them via catch-all, but cannot publish into that namespace. The callback receives an envelope with `topic`, `payload`, `sourceInstanceId` (null for engine-originated events), and a per-engine sequence number. Scratch publications carry source ID `0`; CLI `publish` acts through scratch and reaches other instances' catch-all subscriptions.

Use structured, data-only payloads: JSON-compatible values with explicit size/depth limits, copied across QuickJS runtimes. Reject functions, cycles, oversized messages, and unsupported values at publish time. Publish enqueues a message; delivery happens at a defined host-loop boundary after the publisher's callback returns, never reentrantly. Deliver in publish order and stable subscription registration order. A callback may publish another event for the next delivery turn, with a per-frame dispatch budget so message loops cannot stall rendering. Bound each instance queue and total queued bytes; report overflow explicitly to the publisher and count drops in diagnostics. Do not let a slow or failed subscriber block delivery to the others.

Subscriptions belong to a script instance. Successful reload replaces that instance's subscriptions atomically with the candidate's; failed reload leaves the old subscriptions and queued deliveries intact. Stop removes the subscriptions and drops undelivered messages for that instance. Events published while a target is stopped are discarded for that target; there is no replay on restart. The scratch scene is not reloadable or stoppable through ordinary script commands; its subscriptions and objects live only for the current engine session, ending at shutdown, explicit scratch reset, or an uncaught scratch callback exception. An event already published is delivered to the subscribers eligible at dispatch time; document this rule and test stop/reload during delivery. The bus is in-memory only in the first release: no persistence, replay, or cross-device transport. Keep the dashboard control socket separate from script messaging.

## Saved scene namespaces

Store named saves separately per script. Derive a stable storage key from the script's canonical path, rather than its session instance ID; give scratch instance `0` its own `scratch/` directory. `saveSceneContainer(id, "layout")` and `loadSceneContainer("layout")` continue to use the caller's namespace without changing existing script code. Two scripts can therefore save `layout` independently across engine restarts. Keep the configured `--scene-state-dir` as the root and place script namespaces below it.

Provide an explicit cross-script import such as `importSceneContainer(sourceScript, "layout")`, which reads a save from the named source namespace and restores it into the caller's scene with fresh IDs. Identify the source by a stable script catalog name or key, not a transient instance ID. Validate the source and save name, reject path traversal and symlink escapes, and preserve the existing staged restore behavior on failure. Copy through the normal snapshot validation path; do not share live scene objects or native handles.

Treat existing files in the current shared scenes directory as disposable development/test data. The new layout does not read them automatically and needs no migration command. Document how to remove or recreate those saves when switching layouts. Test same-name isolation, restart persistence, explicit import, and malformed files.

## Dashboard design

Build a separate controller process that registers a SteamVR dashboard tab while SteamVR is running. Engine autostart with SteamVR is optional and disabled by default; the dashboard indicates when the engine is offline and offers a Start Engine button. The CLI also provides `start-engine` when the engine is offline. These startup actions use the same supervised engine service rather than depending on an already running control socket. Once running, the dashboard and CLI connect over a versioned, local Unix domain socket. The engine is authoritative for the script registry and lifecycle; the dashboard can restart or reconnect without stopping scripts. Authenticate with same-user socket permissions, limit request and response sizes, and expose no TCP listener.

The tab lists running, starting, stopped, and failed scripts; provides Launch, Reload, and Stop actions; shows the last error and whether a reload retained the old scene. It alerts on callback-error stops, alongside a SteamVR notification, including when the tab is closed. It also edits the shared autostart configuration and automatic restart setting. Launch uses only the configured scripts directory and its subdirectories, through a bounded catalog of readable `.js` files; the CLI follows the same rule. The UI refreshes at a modest interval while visible and sleeps when hidden. It must not capture controller input outside the dashboard tab.

Use Framecorder's installed `framecorder.vrmanifest` pattern (`launch_type: binary`, `is_dashboard_overlay: true`) and its `framecorder-ui.service` pattern (`BindsTo=steamvr.service`, `After=steamvr.service`) as the initial integration reference. Framecorder's own documentation says its tab attaches only to an existing SteamVR session and sleeps when hidden. Framey instead injects a panel into Steam's local web interface; that route depends on an internal debug port and UI structure. Prototype the native dashboard tab first, then evaluate Framey/Deckloader compatibility as an optional integration. The control process must never start SteamVR implicitly.

## CLI and live REPL

Provide a `pocketspace-cli` command with `start-engine`, `list`, `catalog`, `start`, `stop`, `reload`, `status`, `stats`, `watch`, `publish`, `scratch reset`, `autostart list/add/remove`, `eval`, and `repl` subcommands. `start-engine` works while the control socket is offline. `list` and `status` expose stable instance IDs, names, paths, lifecycle state, uptime, last error, and reload result. `stats` provides engine totals and per-script metrics. `watch` streams status, resource, error, and bus-drop updates. `publish` injects a data-only event from scratch instance `0`; the dashboard and CLI share the same control socket, while scripts still receive messages through the in-engine bus.

`repl` defaults to reserved instance `0`, a persistent scratch QuickJS context **with its own scene and the normal scene API**. It can create objects, panels, and physics, launch and stop user scripts through explicit management bindings, inspect status, and publish events. Exiting the CLI leaves scratch objects and globals running; `scratch reset` deliberately clears and recreates only instance `0`. Multiple CLI clients share scratch instance `0`, so submissions are serialized on the host thread and tagged by request ID. `:enter <instance-id>` switches subsequent JavaScript submissions to that live script's existing context; `:leave` returns to scratch. Provide `:where` and `:help`. The prompt shows scratch or the selected instance and generation. On a user-script reload or stop, return to scratch and require another `:enter` so an operator cannot accidentally affect a replacement scene. Provide `eval --code <text>` / `eval --file <path>` for one-shot scratch use and `eval --script <instance-id> ...` for targeted live use. In noninteractive calls, a target's instance generation must be supplied or obtained during a preceding status lookup; stale generations fail clearly. `eval` and REPL must report JavaScript results, exceptions, and `print()` output without mixing results from other scripts; tag captured output with instance and request IDs. Document that live evaluation mutates the current scene immediately and is not a transactional script reload.

For an LLM harness, every command must run without a TTY, support `--json` with one versioned JSON response on stdout, send diagnostics to stderr, use stable exit codes, and accept a configurable connection/operation timeout. `watch --json` emits one JSON object per line with sequence IDs and reconnect/loss markers. Include request IDs and instance generations so a harness can identify stale targets. Retain bounded recent command outcomes by request ID for duplicate detection; after a timeout, the harness queries the outcome before retrying a mutation. Never automatically resubmit an `eval` whose outcome is unknown. Supply a `--wait` option for launch/reload completion and a bounded `--limit` or duration for watch commands. Never emit terminal control codes or interactive prompts in JSON mode. Document exact schemas and examples for shell, Python, and an agent harness.

Bound submitted source length, returned output, queued console messages, and execution time. Use QuickJS's interrupt mechanism where feasible; verify that it stops a tight JavaScript loop without killing the engine. Native binding calls must also have bounded work; an interrupt cannot preempt an indefinitely blocked native call. Surface a timeout or failed evaluation as that instance's error and keep other scripts running. Same-user socket access grants code execution in the engine's user account, so document the trust boundary and keep the socket private.

## Resource reporting

Show process FPS, CPU, RSS, and DRM GPU memory once as **engine totals**. Per script, report QuickJS heap usage from its runtime, object/panel/asset/body counts, owned estimated CPU/GPU allocations where ownership is clear, and measured callback/update time over a rolling window. Label these as per-script values or estimates. Report shared renderer, compositor, input, shader-cache, and driver allocations separately or as unallocated process overhead; do not divide totals evenly or sum shared RAM and GPU memory. Add optional per-script render and physics time only after instrumentation measures their boundaries reliably. Record sample interval and unavailable values.

## Implementation slices

1. **Ownership map and baseline checks.** Enumerate every process-global scene pointer, callback, overlay key, input queue, grab/hover state, renderer cache, statistics value, and persistence path. Add focused regression coverage for two scenes with colliding numeric IDs and for unchanged one-script behavior. Record a representative one-script FPS/memory baseline on Deckard before comparing a matched two-script workload after multi-instance rendering exists; neither measurement may capture pointer input.
2. **Instance registry and lifecycle.** Introduce stable instance IDs and scoped scene access, including persistent scratch instance `0`. Support zero-user-script idle mode by default, an explicit validated autostart list, automatic file-change reload, and independent candidate load/reload/stop. Ensure failure of one autostart, candidate, or callback does not tear down another. Use the catalog launch path for one or many scripts.
3. **Shared frame and interaction.** Route one tracking/input snapshot into all instances, arbitrate picking/grabs globally by closest hit, qualify overlay and surface keys, render all live scenes in stable order, and cleanly detach only the stopped/reloaded instance. Define behavior for overlapping panels and model surfaces. Add per-script scene-save namespaces and explicit cross-script import; verify cross-script closest-hit selection, held-object release, physics separation, save-name isolation, import, and reload under live rendering.
4. **Event bus.** Add bounded publish/subscribe with exact-topic and cross-instance-only catch-all delivery, copied payloads, deterministic ordering, deferred dispatch, scoped subscriptions, and failure isolation. Test two scripts exchanging events, own-topic delivery through exact subscriptions, own-topic exclusion from catch-all, scratch-to-script delivery, subscriptions to engine-originated topics, rejection of script publications to `engine.*`, multiple matching subscriptions, no-subscriber topics, a publish from a subscriber, overflow, malformed payloads, and reload/stop during delivery.
5. **Control protocol and catalog.** Add a versioned local socket API for list/catalog/launch/reload/stop/status/stats/watch/publish/autostart/scratch/eval. Queue mutations and evaluations onto the host thread; use request IDs, instance generations, and structured errors. Validate paths against the configured catalog and write shared settings atomically; revalidate external file edits. Test malformed requests, stale IDs, duplicate launches, concurrent requests, disconnects, and engine restart.
6. **CLI and REPL.** Implement human-readable interactive commands and deterministic JSON one-shot commands against the protocol. Add persistent scene-owning scratch instance `0`, explicit `:enter`/`:leave` script context switching and scratch reset, safe-boundary evaluation, output capture, time/size limits, and explicit reload reattachment. Test shared scratch access from two clients and an LLM harness invoking commands without a TTY, parsing JSON, handling timeouts, and retrying without duplicate starts or evaluations.
7. **Telemetry.** Add per-runtime QuickJS memory and per-script counts/timers, plus bus queue depth and dropped-message counts. Surface process totals separately. Verify timing overhead and accounting on one and two-script scenes; mark unavailable metrics explicitly.
8. **Dashboard tab.** Register a separate native dashboard application, package a user service tied to SteamVR plus an optional engine-autostart setting that is off by default, and build the launch/monitor/stop UI against the socket. Provide an offline Start Engine action, SteamVR notifications, and dashboard alerts for script errors. Confirm dashboard open/close, pointer focus, reconnect, engine absence, and SteamVR restart behavior in the headset.
9. **Migration and release checks.** Update CLI, lifecycle, architecture, JavaScript/statistics, event-bus and CLI guides, setup, test index, and examples. Run relevant native regressions, `python3 tools/lint-docs.py`, `npm run docs:build` for site changes, `git diff --check`, and a measured two-script soak on Deckard. User headset validation should confirm visibility, input arbitration, dashboard controls, and simultaneous scenes. Stop test demos afterward.

Complete each slice and its checks before starting the next. Keep experimental flags and test scenes separate from production defaults until equivalent workload measurements support them.

## Slice 1 decisions

- **World anchor: resolved.** Use the existing engine-level anchor for all instances. `src/main.cpp` already establishes one anchor at startup and applies it to tracking, model, and panel transforms. Verify two-script picking and placement against that shared anchor.
- **Callback failure: resolved.** An uncaught `update()` or event-callback exception stops only its instance and records an error for the CLI/dashboard. Verify cleanup and the state of other scripts.
- **Startup: resolved.** Start no user scripts by default. Only the explicit autostart list launches user scripts on engine startup; scratch instance `0` remains available.
- **Saved scene names: resolved.** Scope saves by a stable script-path-derived key, with a separate scratch namespace. Add explicit import from a named source script. Existing shared-directory development/test saves may be deleted or recreated; no migration is required.
- **Stopped-entry history: resolved.** Show running and stopped entries from the current engine session only. Clear that history when the engine restarts; the script catalog and explicit autostart list remain available.
- **Script catalog: resolved.** Launch user scripts only from the configured directory, including through the CLI.
- **Duplicate launches: resolved.** Allow one live instance per canonical script file; reject a duplicate start.
- **File updates: resolved.** Automatically reload a running script when its file changes, preserving the current transactional reload behavior.
- **Overlapping input: resolved.** Choose the closest eligible model-ray hit, with stable instance ID breaking equal-distance ties. SteamVR chooses native panel pointer targets.
- **Stopped-script events: resolved.** Deliver only to currently running subscribers; discard events for stopped scripts.
- **Autostart editing: resolved.** Dashboard, CLI, and direct file edits use the same validated configuration file.
- **Scratch callback failure: resolved.** Reset scratch instance `0` without stopping user scripts.
- **Engine autostart: resolved.** Make startup with SteamVR optional and disabled by default.
- **Script directory: resolved.** Use a separate configurable user scripts directory rather than the repository example directory.
- **Error recovery: resolved.** Notify with a SteamVR notification plus dashboard alert. Use one global automatic-restart setting, off by default; enabled retries must be paced and bounded.
- **Scratch persistence: resolved.** Scratch instance `0` lasts only for the current engine session.
- **Offline dashboard behavior: resolved.** Offer a Start Engine button when the engine is not running.
- **Offline CLI behavior: resolved.** Offer `start-engine` even when the control socket is unavailable.
- **Catalog recursion: resolved.** Discover scripts in subdirectories of the configured user scripts directory.
- **Manual stop: resolved.** Keep a manually stopped script stopped for the current engine session, even if it is on the autostart list; retain its autostart entry for the next engine start.
